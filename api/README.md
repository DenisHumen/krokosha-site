# api/ — Go API и CLI

Go-модуль с корнем в этой папке. Минимальная версия Go — в [`go.mod`](go.mod); CI собирает именно на ней.

**Статус:** бэкенд по плану готов ([docs/roadmap.md](../docs/roadmap.md)): синхронизация с GitHub (`krokosha-cli sync`), сервис `krokosha-api` (конфигурация, MySQL с миграциями, Redis с деградацией в память, `/api/health`), аналитика с гео и дневными итогами, админка (вход с 2FA, обзор с живой лентой, визиты, экспорт, трафик сервера, статус системы, заявки, «Входящие», бот), приём заявок (антиспам, outbox, письма), Telegram-бот, ответы клиентов письмом, оповещения владельца, IndexNow. На VPS ещё не выложен.

## Команды

```bash
go test ./...                                  # unit-тесты (интеграционные пропускаются)
docker compose -f compose.test.yaml up -d --wait   # одноразовые MySQL и Redis для интеграционных тестов
KROKOSHA_TEST_MYSQL=127.0.0.1:33306 KROKOSHA_TEST_REDIS=127.0.0.1:36379 go test ./...
go run ./cmd/krokosha-cli sync -v              # синхронизация с GitHub → ../content/generated/
go build -trimpath -o bin/ ./cmd/...           # бинарники (на сервере — CGO_ENABLED=0, один статический файл)
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.13.2 run ./...   # линтер, как в CI
dev/run-local.sh                               # админка на этой машине с демо-данными → http://localhost:8099/_dev/
```

`dev/run-local.sh` поднимает одноразовые MySQL и Redis, создаёт администратора `dev` (пароль печатается), заливает две недели демо-визитов ([`dev/seed-demo.sql`](dev/seed-demo.sql)) и десяток выдуманных заявок во всех статусах, с перепиской ([`dev/seed-demo-leads.sql`](dev/seed-demo-leads.sql)), генерирует access-лог nginx за те же две недели ([`dev/demolog`](dev/demolog/main.go)) и запускает API. К серверу отношения не имеет.

`GITHUB_TOKEN` — необязательный fine-grained токен с доступом только на чтение публичных репозиториев. Без него GitHub даёт 60 запросов в час; благодаря кэшу этого хватает, но первый запуск может дособрать метрики только со второго раза.

## `krokosha-api`

Один процесс под systemd на `127.0.0.1:8080`, за nginx. Настройки — из окружения (`/etc/krokosha/env`, описание в [`deploy/env/.env.example`](../deploy/env/.env.example)); адрес прослушивания обязан быть loopback — сервис доверяет заголовку `X-Real-IP`, который ставит nginx.

- **MySQL** — источник истины. Сервис ждёт базу до 90 секунд (после перезагрузки контейнер может стартовать позже) и применяет миграции из [`migrations/`](migrations/): файлы `NNNN_описание.sql`, каждая ровно один раз, под блокировкой `GET_LOCK` — два одновременно стартующих экземпляра не мигрируют параллельно. DDL в MySQL не откатывается, поэтому миграции пишутся повторяемыми (`CREATE TABLE IF NOT EXISTS`), а версия записывается только после успеха.
- **Redis** — быстрое и временное (`internal/cache`). Необязателен: если `REDIS_URL` пуст или Redis недоступен, лимиты считаются в памяти процесса, в журнале одна строка на сбой и одна на восстановление.
- **`GET /api/health`** — `200 ok`, пока доступна база; без Redis — `200 degraded`; без базы — `503`. Подробности (версия, проверки) видны только при обращении с самого сервера, посетителю отдаётся голый статус.

### Аналитика (`internal/analytics`, бриф B5)

`POST /api/e` принимает пачки событий от [`/assets/analytics.js`](../web/public/assets/analytics.js) — читаемого скрипта на 2,9 КБ gzip без cookie.

- **Посетитель** — `sha256(соль дня + IP + User-Agent)`, 16 байт. Соль меняется каждый день, старые удаляются через двое суток: визиты разных дней нельзя связать, даже имея всю базу. IP хранится только усечённым (`/24`, `/48`), в Redis адресов нет вовсе — ключи лимитов строятся из солёного хэша.
- **Не записываются:** посетители с `DNT: 1` или `Sec-GPC: 1` (скрипт и так молчит, сервер — второй замок), боты по User-Agent, запросы со страниц других сайтов (`Origin`).
- **Строгая схема:** неизвестные поля, путь с query-строкой, referrer с путём, идентификаторы с разметкой — `400`. Всё принятое попадёт в базу и на экран админки.
- **Запись:** очередь в памяти, раз в секунду одна транзакция; глубина скролла и время на странице — свойства просмотра (`GREATEST`), а не отдельные строки. При остановке сервиса очередь дописывается.
- **Визит** — тот же посетитель с паузами не длиннее 30 минут (границы — в Redis). **«Сейчас на сайте»** и живая лента для админки — оттуда же.
- Отчётный день считается в часовом поясе владельца (`content/site.yaml → timezone`).
- **Страна и город** (`internal/geo`) — по локальной базе в формате MaxMind DB (`GEOIP_DB`; на сервере установщик ставит туда DB-IP City Lite `/var/lib/GeoIP/dbip-city-lite.mmdb`, которую раз в месяц обновляет `krokosha-dbip.timer`, или, с ключом MaxMind, GeoLite2 `/var/lib/GeoIP/GeoLite2-City.mmdb` от `geoipupdate`; без настройки — GeoLite2; `off` — не определять). Спрашивается полный адрес, хранится ответ; файл замечается сам — и когда появится, и когда его заменит новая версия (проверка раз в 10 минут; сломанный файл не отнимает старый). Без базы колонки пустые, «География» в обзоре — «не определена». Экран «Статус системы» показывает, какая база загружена и когда собрана, и предупреждает, если ей больше шести недель. Лицензии баз просят назвать их там, где видны результаты: внизу каждой страницы админки — «IP Geolocation by DB-IP» (CC BY 4.0) или строка GeoLite2. Названия стран в админке — по-русски (CLDR через `x/text`), города — как в базе, по-английски.
- **Срок хранения** (`internal/analytics/rollup.go`, `ANALYTICS_KEEP_MONTHS`, по умолчанию 12; 0 — бессрочно). Раз в 6 часов закончившиеся дни (через час после полуночи владельца, когда последние просмотры дописали время на экране) суммируются в `analytics_daily` и `analytics_daily_breakdown` (по 50 строк на измерение: страницы, языки, устройства, браузеры, системы, страны, сайты, источники, кампании, клики, внешние переходы, пасхалки, секции по охвату и по времени). Сырые просмотры и события старше срока удаляются порциями — **только те дни, итоги которых уже есть**. Обзор периода, который вышел за срок, строится из итогов и говорит об этом на экране; часы, список визитов и экспорт за такой период недоступны.

### Заявки: приём (`internal/leads`, `internal/outbox`, `internal/mail`, бриф B10.1–B10.2)

`POST /api/leads` принимает форму с сайта: обычную (`application/x-www-form-urlencoded`, посетитель без JavaScript) и `FormData` от скрипта (`Accept: application/json`). Контракт разметки — [docs/contract.md §7](../docs/contract.md).

- **Проверка** — те же правила, что в скрипте формы, но сервер им не верит: имя, контакт (почта; `@ник` или ссылка t.me; телефон — приводятся к одному виду), направление из `content/site.yaml`, описание 20–4000 символов, согласие. Управляющие символы вычищаются, имя — одна строка. Бюджет и сроки приходят порядковым номером и сохраняются английской подписью: в админке один язык.
- **Антиспам без сторонних сервисов, по баллам:** скрытое поле-ловушка (100), proof-of-work не пройден (45) или отсутствует — форма отправлена без JavaScript (35), заполнено быстрее 4 секунд (50), ссылки в описании (25 за каждую, до 50), ссылка в имени (40), стоп-слова (30), текст заглавными (15). От 60 баллов заявка получает статус `spam`: **отправитель видит обычное «спасибо»**, уведомления никому не уходят, в админке заявка видна и возвращается одним кликом. Без JavaScript и без ссылок заявка проходит.
- **Proof-of-work** совместим с [ALTCHA](https://altcha.org): `GET /api/leads/challenge` выдаёт задачу — найти число N < 30 000, для которого `SHA-256(salt + N)` равен заданному; ~1 с на телефоне. Задача подписана HMAC (`APP_SECRET`), живёт 45 минут, одно решение принимается один раз. Соль заканчивается разделителем `&` — иначе цифры можно перенести из числа в соль и продлить срок. Время от выдачи задачи до отправки и есть «время заполнения».
- **Лимит** — 3 заявки в час с адреса (ключ в кэше — HMAC адреса, самого адреса там нет). Ошибки в полях лимит не расходуют.
- **Одна транзакция** (B10.2): заявка, её первое сообщение, запись в истории и задачи на уведомления в `outbox` — либо всё, либо посетителю предлагают повторить. К заявке копируется сводка анонимной сессии аналитики: источник, UTM, устройство, какие секции смотрел, сколько времени (о чём сказано на `/privacy`).
- **Без JavaScript** ответ — `303` на `/api/leads/thanks?t=<случайный токен заявки>`: собранная Astro страница «спасибо» из живого релиза, в которую подставлены номер и ссылка на бота. Перезагрузка страницы не отправляет форму повторно; по чужому токену ничего не увидеть. Ошибки возвращают на форму: `/<язык>/#form-error-…`, блок показывает CSS `:target`.
- **Outbox** — задачи `lead.notify` (почта владельцу, Telegram всем допущенным) и `lead.autoreply` (клиенту, если он оставил почту). Воркер доставляет с паузами 30 с → 2 мин → 10 мин → 30 мин → 2 ч → 6 ч → 12 ч → 24 ч, затем сдаётся (`failed`, видно на экране статуса). Ключ идемпотентности (`lead:42:notify:email`) не даёт поставить задачу дважды; «зависшая» доставка освобождается по времени; задачи канала, который ещё не настроен (нет SMTP, нет бота), ждут и попыток не тратят. Постоянные отказы (SMTP 5xx) не повторяются. Письмо собирается в момент отправки, а не постановки: сутки пролежавшая задача не отправит вчерашние данные.
- **Письма** — `multipart/alternative` (текст + HTML на таблицах и inline-стилях, с `<html lang>` и `<title>` = тема), всё введённое посетителем экранируется `html/template`. Владельцу: карточка заявки целиком, `Reply-To` — клиент, кнопка «Открыть в админке». Клиенту — на языке страницы, `Auto-Submitted: auto-replied` (почтовые роботы на такое не отвечают). Отправка — SMTP на `SMTP_ADDR` (STARTTLS, на localhost без проверки имени сертификата); пока `SMTP_ADDR` пуст, письма ждут в outbox.
- **Письмо клиенту не повторяет свободный текст посетителя.** В нём номер заявки, выбранные направление, бюджет и сроки (на языке письма), контакт, число файлов и фраза «сообщение сохранено вместе с заявкой». Описания, имён файлов и «имени», которое не похоже на имя (ссылка, цифры, больше четырёх слов или 40 символов — `greetingName`), в нём нет: подтверждение уходит на адрес, который мог ввести кто угодно, и форма, повторяющая присланный текст, стала бы бесплатной рассылкой чужого спама с нашего домена. Бриф просил «копию отправленного»; от неё осталась сводка выбранного.
- **Что ещё держит письма вне спама.** `From` всегда с именем: из `MAIL_FROM` (`--mail-name` установщика), а без него — владелец из `content/site.yaml` (`profile.name` и `nickname`: «Denis (Krokosha)»). Ссылки в письмах клиенту ведут только на домен сайта: «Продолжить в Telegram» — это `GET /api/leads/telegram?t=<токен заявки>`, которая отвечает `302` на `https://t.me/<бот>?start=c_<токен>` (заявка удалена, помечена спамом или бота нет — `302` на сайт; никуда больше этот адрес не ведёт). Текстовая и HTML-версии несут одни и те же ссылки. `Message-ID` (`lead-42.autoreply.<метка>@домен`) одинаков при каждой попытке доставки, а метка — HMAC от `APP_SECRET`: после переустановки номера заявок начинаются с единицы, и почтовый ящик, где уже лежит письмо с таким же ID, молча выбросил бы новое.

Тесты: форма → база → outbox → тестовый SMTP-сервер (`internal/mail/mailtest`), сбой почты и повтор, экранирование `<script>` / эмодзи / очень длинного текста, подделка и повторное использование proof-of-work, перекройка соли.

### Почта: адрес для ответов и конверт (`internal/leads/replyaddr.go`, `internal/mail`, бриф B10.5)

- Письма клиенту (подтверждение и ответы) несут `Reply-To: leads+k-0042.<подпись>@<домен>`. Всё после «+» почтовый сервер при выборе ящика игнорирует, а сервису оно говорит, к какой заявке относится ответ. Подпись — HMAC-SHA256 от номера на `APP_SECRET`, 80 бит в base32: написать в чужую заявку, подобрав номер, нельзя; регистр адреса не важен (почтовые программы меняют его как хотят).
- Уведомление владельцу по-прежнему несёт `Reply-To` клиента — на него можно ответить из обычной почтовой программы.
- Конверт (`MAIL FROM`) — служебный ящик `MAIL_INBOX`, заголовок `From` — владелец: почтовый сервер разрешает учётной записи отправлять только от своего адреса, а возвраты (bounce) приходят туда же, куда и ответы клиентов.

### Почта: ответы клиентов (`internal/imap`, `internal/inbox`, бриф B10.5)

Сервис держит соединение с ящиком `MAIL_INBOX` по IMAP (`IMAP_ADDR`, `IMAP_USER`, `IMAP_PASSWORD`; TLS с первого байта) и ждёт письма командой IDLE — без опроса: письмо попадает в заявку через секунду-другую после доставки. Оборвавшееся соединение восстанавливается само, с растущими паузами. Без `IMAP_ADDR` почта просто не читается, остальное работает.

- **IMAP — своими руками** (`internal/imap`, стандартная библиотека): вход (SASL PLAIN, иначе LOGIN), `SELECT`, `UID SEARCH`, `UID FETCH … BODY.PEEK[]`, флаги, `UID EXPUNGE`, `IDLE`. Нужна дюжина команд одному серверу, который ставит наш же установщик; длина строк и размер литералов ограничены. `imaptest` — почтовый ящик в памяти для тестов, тоже по TLS.
- **Куда письмо:** (1) адрес с подписью `leads+k-0042.<подпись>@…` среди получателей (`To`, `Cc`, `Delivered-To`, `X-Original-To`, `Received … for`) — в эту заявку, с какого бы адреса клиент ни ответил; (2) номера нет, но отправитель оставлял заявку с этим адресом — в его последнюю заявку, с пометкой в истории «привязано по адресу отправителя»; (3) иначе — на экран **«Входящие без заявки»**. Номер без верной подписи ничего не открывает.
- **Что берётся из письма:** текст (`text/plain`, иначе HTML без разметки), кодировки windows-1251 / koi8-r и прочие из списка браузеров, RFC 2047 и RFC 2231 в именах. **Цитата отрезается** (`quote.go`): «On … wrote:» на английском, русском и украинском, в том числе перенесённое на 2–3 строки, строки с `>`, «-----Original Message-----», блок заголовков Outlook (`От:` / `Отправлено:`), в HTML — `blockquote`, `gmail_quote` и подобные. Ответ, вписанный между строк цитаты, сохраняется целиком; когда сомнительно — остаётся больше, а не меньше.
- **Вложения** проходят ту же проверку, что файлы формы (`leads.Inspect`: тип по содержимому, до 10 МБ), не больше пяти на письмо; картинки подписи (inline, меньше 24 КБ) молча пропускаются. Что не принято — названо в истории заявки. Файлы лежат там же, в `attachments/`, и отдаются только админкой; в Telegram уходит «📎 файлов: N — в админке».
- **Автоответы и рассылки** (`Auto-Submitted`, `Precedence`, `List-*`, `noreply@`) в переписку попадают с пометкой «[автоответ]», но заявку в работу не возвращают и никого не будят.
- **Письмо вернулось** (`multipart/report`): сервис находит заявку по подписанному адресу в возвращённых заголовках (`Reply-To` нашего письма) — «K-0042» в тексте отчёта может напечатать кто угодно. Ответ помечается «не доставлено», в истории — причина (`5.4.4 Host not found`), сотрудники узнают об этом в Telegram и письмом: клиент, не получивший ответа, иначе ждал бы молча.
- **После разбора письмо из ящика удаляется** — текст и файлы уже в заявке и исчезнут вместе с ней (удаление данных клиента, обезличивание). Журнал `inbox_letters` хранит для таких писем только хэш `Message-ID`: одно письмо обрабатывается один раз, даже доставленное дважды или при остановке сервиса между базой и ящиком (запись журнала — в одной транзакции с сообщением).
- **Письма без заявки остаются в ящике** (помечены прочитанными), в базе — отправитель, тема и начало текста для экрана. Файлы такого письма не распаковываются, пока человек не скажет, чья это заявка. На экране — «В переписку заявки» (номер вводится как угодно: `#K-0042`, `k-42`, `42`; письмо перечитывается из ящика целиком, с файлами) и «Удалить письмо». Через `LEADS_SPAM_DAYS` дней (30) неразобранные письма удаляются из ящика и журнала.
- **Неверный пароль ящика пробуется один раз.** Повторные попытки заблокировали бы сервис в fail2ban почтового сервера — а с ним и исходящую почту сайта. Экран «Статус» показывает, читается ли ящик, когда проверен, сколько писем ждут решения.
- Письмо читается с защитой от паники разборщика: что бы в нём ни было, сервис не падает — письмо уходит во «Входящие» с пометкой «не удалось разобрать».

Тесты: письмо с цитатой и вложением в виде, в каком его шлёт Gmail (требование брифа B10.7); десяток видов цитирования; старые кодировки; HTML-письмо; отчёт о недоставке, настоящий и поддельный; письма, собранные во вред (пятьдесят уровней вложенности, тысяча вложений, файл больше лимита, программа под именем `.pdf`); дубликаты; удалённая заявка; живое ожидание IDLE и переподключение после обрыва.

### Админка: вход (`internal/auth`, `internal/admin`, бриф B6)

Серверные страницы под секретным путём `ADMIN_PATH` (например `/_k7f3a9/`). Любой другой путь — обычный 404: угадать, что админка существует, нельзя. Только HTTPS.

- **Пароль** — argon2id (64 МБ, 3 прохода), формат PHC, минимум 12 символов. Одновременно считается не больше двух хэшей: подбор паролей не может занять память сервера. Несуществующий логин проверяется так же долго, как существующий.
- **Двухфакторная аутентификация** — TOTP (RFC 6238), включается на странице «Аккаунт». QR-код рисует сам сервер: секрет не уходит сторонним «генераторам QR». Код одноразовый: принятый шаг записывается, повтор того же кода не пройдёт. Вход в два шага — пароль в страницу не возвращается, между шагами живёт одноразовый билет (5 минут, 5 попыток).
- **Сессия** — случайный токен в cookie `__Host-ks` (`Secure`, `HttpOnly`, `SameSite=Strict`, без `Domain`); в базе лежит только его SHA-256. Живёт 2 часа без активности и не дольше суток. Смена пароля завершает остальные сеансы; на странице «Аккаунт» виден список сеансов, любой можно завершить.
- **Формы** — CSRF-токен на каждый сеанс, плюс проверка `Origin` и `Sec-Fetch-Site`.
- **Подбор** — не больше 10 попыток на логин и 20 на сеть за 15 минут (считает Redis, без него — память процесса); сверху — лимит nginx на форму входа и fail2ban ([deploy/README.md](../deploy/README.md)).
- **Заголовки** — `Cache-Control: no-store`, `X-Robots-Tag: noindex`, CSP без единого inline-скрипта и стиля: графики рисуются на сервере (SVG).
- **Журнал** — таблица `audit_log`: входы, отказы, смена пароля, 2FA, завершение сеансов; адрес — усечённый, как везде.

### Админка: экраны (`internal/admin`, отчёты — `internal/analytics/report.go`)

- **Обзор** — как на референсе `ref-03`: таймлайн визитов (по часам за день, по дням за неделю, месяц или свой диапазон; рекламный трафик — отдельным цветом), крупные цифры, «сейчас на сайте», живая лента, секции по времени и по охвату, глубина прокрутки, кольца конверсий (Telegram, почта, GitHub — в % от посетителей), источники, сайты, UTM-кампании, страницы, языки, клики, внешние переходы, пасхалки, устройства, страны.
- **Визиты** — анонимный посетитель → путь по страницам, секциям и кликам по времени. Посетитель — псевдоним на один день, адрес — усечённый.
- **Живая лента** — Server-Sent Events (`/live`): число посетителей раз в 10 секунд и события по мере поступления. Поток не считается активностью администратора (открытая вкладка не продлевает сеанс), закрывается вместе с сеансом и раз в полчаса переустанавливается. Через nginx идёт без буферизации (`X-Accel-Buffering: no`).
- **Экспорт** — просмотры и события за период в CSV (UTF-8 с BOM, время — UTC). Ячейки, которые таблица приняла бы за формулу (`=`, `+`, `-`, `@`), обезврежены: UTM-метки пишет кто угодно, а файл открывает владелец. Каждая выгрузка — в журнале действий.
- **Графики** рисует сервер (SVG) — в админке нет ни графических библиотек, ни inline-стилей; единственный скрипт (`static/admin.js`) подключает живую ленту. Без JavaScript всё, кроме ленты, работает так же.
- **Владелец — не посетитель:** запросы к `/api/e` с cookie админки не записываются.
- Отчётный день, часы на графике и время в ленте — в часовом поясе владельца; переход на летнее время не сдвигает и не теряет дни (покрыто тестами).

### Заявки в админке (`internal/leads/crm.go`, `internal/admin/leads.go`, бриф B10.4, B10.6)

Мини-CRM. Всё, что делает экран, — это метод `leads.Store`; бот (шаг 6) будет вызывать те же методы, поэтому «кто взял заявку» и статусы не могут разойтись между админкой и Telegram.

- **Список и доска.** Список — с поиском по имени, контакту, тексту и номеру (`#K-0042`, `K-42`, `42`), вкладки по статусам со счётчиками, по 50 на страницу; спам — отдельной вкладкой и в общий список не попадает. Доска — пять колонок по статусам, карточка перетаскивается мышью (`static/admin.js`, обычный HTML5 drag-and-drop); разрешён ли переход, решает сервер — при отказе карточка возвращается, причина показывается. Без JavaScript те же кнопки есть на карточке заявки.
- **Статусы** (B10.4): `new → in_progress → waiting_client → done`, `rejected`, `spam`; разрешённые переходы — таблица `transitions`, остальное сервер отклоняет (409). Закрытую заявку можно вернуть в работу: ошибка не должна быть окончательной. Каждый переход пишется в историю заявки: кто, когда, откуда и куда.
- **«Взять в работу»** — `UPDATE … WHERE status = 'new'`: из двух одновременных нажатий строку «новой» застаёт только одно. Второй получает ответ «заявку уже взял(а) …» — с именем. Тест: восемь одновременных «взять», успех ровно один.
- **Карточка** — лента как в мессенджере: сообщения клиента, ответы (с отметкой «ждёт отправки / доставлено / не доставлено»), внутренние заметки (клиент их не видит), события истории; справа — клиент, статус, сводка визита со ссылкой на путь по сайту, оценка антиспама с причинами.
- **Ответ клиенту** уходит тем каналом, который клиент выбрал в форме: почта — письмом (задача `lead.reply` в outbox, в одной транзакции с сообщением), Telegram — через бота (задача ждёт шага 6), телефон — ничего не отправляется, текст — это запись итога звонка. Первый ответ останавливает счётчик «времени первой реакции» и переводит заявку в «Ждём клиента»; ответ по закрытой заявке её не открывает. Письма по одной заявке складываются у клиента в одну цепочку (`In-Reply-To`/`References`; Message-ID детерминированы, повтор доставки не создаёт второго письма). Если доставка сдалась — сообщение помечается «не доставлено».
- **Шаблоны** ответов и отказов на трёх языках — таблица `reply_templates`, редактор на странице «Шаблоны»; на карточке предлагаются шаблоны на языке клиента, `{name}` и `{id}` подставляются. Стартовый набор кладёт миграция `0006` — только в пустую таблицу, правки владельца она не трогает. Отказ можно отправить письмом или закрыть заявку молча; причина отказа сохраняется.
- **Заявка, спасённая из спама** («Не спам»), объявляется как новая: уведомления, которые для спама не ставились, ставятся в момент возврата.
- **Воронка за 30 дней:** сколько пришло, в работе, ждут клиента, завершено, отклонено, спам; медиана времени первой реакции (медиана, а не среднее: одна заявка, отвеченная после отпуска, не должна портить число); откуда приходят заявки и сколько из них завершено — по источникам и рекламным кампаниям.
- **«Клиент ждёт ответа»** — метка на открытых заявках, где последнее слово за клиентом.
- **Экспорт CSV** всех заявок (те же правила, что у экспорта аналитики: BOM, обезвреженные формулы, запись в журнале).
- **Удаление данных по запросу клиента** (B10.6): заявка, переписка, заметки, история и неотправленные уведомления удаляются одной транзакцией; подтверждение — номер заявки, набранный руками. В журнале действий остаётся одна строка: номер, кто и когда удалил — о человеке ничего.

Тесты: гонка за заявку, таблица переходов, спасение из спама, ответы и заметки (в том числе «телефонные»), кто ждёт ответа, поиск (включая `%` и `_` как обычные символы), воронка и медиана, удаление без следов, шаблоны; для экранов — права (без сеанса и без CSRF ничего не работает), отказ во втором «взять», экранирование введённого посетителем.

### Вложения и срок хранения (`internal/leads/files.go`, `attachments.go`, `retention.go`, бриф B10.1, B10.7)

**Вложения выключены**, пока в `content/site.yaml` не написано `contacts.form.attachments: true`. Тогда сборка сайта добавляет в форму поле «Файлы», а API начинает их принимать — без перезапуска: `site.yaml` перечитывается при изменении.

- **Пределы:** до 3 файлов по 10 МБ; pdf, png, jpg, txt, docx. Пока вложения выключены, форма читается до 48 КБ и ни байтом больше; запрос с файлом получает `files_disabled`.
- **Тип — по содержимому, а не по имени** (`Inspect`): сигнатуры PDF / PNG / JPEG; docx — это zip, в оглавлении которого есть `[Content_Types].xml` и `word/document.xml` (читается только оглавление, ничего не распаковывается — «zip-бомба» ничего не стоит); txt — текст в любой 8-битной кодировке, но без нулевых байтов и управляющих символов. Расширение должно совпасть с тем, что внутри: `invoice.pdf` с программой внутри — `file_type`.
- **Порядок:** файлы проверяются вместе с полями — ошибки в них не расходуют лимит «3 заявки в час». На диск файлы пишутся в последнюю очередь: после лимита, proof-of-work и оценки антиспама. **Файлы роботов не сохраняются вовсе** — в истории заявки остаётся «вложения не сохранены (N)».
- **Хранение:** `<KROKOSHA_DATA>/attachments` (`/srv/krokosha/attachments`) — вне всего, что раздаёт nginx, каталог `0700`, файлы `0600`, владелец — сервис. Имя на диске — 32 случайные шестнадцатеричные цифры; присланное имя очищается (`CleanFilename`: без путей, управляющих символов, не длиннее 100 знаков) и живёт только в базе. Открыть можно только файл с «нашим» именем — что бы ни оказалось в базе.
- **Выдача** — только из админки, только администратору со входом, и только как загрузка: `Content-Disposition: attachment`, `application/octet-stream`, `nosniff`, `CSP: sandbox`. Что бы ни лежало в файле, браузер его сохраняет, а не показывает и не исполняет. Файл выдаётся лишь по адресу своей заявки.
- **Письма** называют файлы (имя и размер), сами файлы по почте не ходят.
- **Удаление данных клиента** удаляет и файлы. Если файл не удалился сразу (или запрос оборвался между записью файла и записью заявки), его уберёт ежедневная уборка: файлы без строки в базе старше суток удаляются.

**Срок хранения** (B10.7, обещан на `/privacy`): раз в сутки заявки, с которыми 24 месяца ничего не происходило, **обезличиваются** — имя, контакт, текст, вся переписка с заметками и файлами, сеть, ссылка на визит и ссылка клиента на заявку удаляются; остаются даты, статус, направление, бюджет, источник и страна — из них складывается воронка. В истории заявки появляется запись «обезличена», в админке — пометка. То, что поймал антиспам, удаляется целиком через 30 дней. Настройки — `LEADS_KEEP_MONTHS`, `LEADS_EXPIRED=anonymize|delete`, `LEADS_SPAM_DAYS` ([`deploy/env/.env.example`](../deploy/env/.env.example)).

Тесты: каждый тип и каждая подделка (программа с расширением pdf / txt / png, архив и таблица под видом docx, оборванный архив, png под видом jpg, html, svg, двойное расширение, пустой файл, путь в имени); права на файлы; отказы не оставляют ничего на диске и не расходуют лимит; файлы робота; удаление; письма; выдача из админки (заголовки, чужая заявка, без входа); обезличивание — что исчезает и что остаётся; режим удаления; уборка.

### Telegram-бот: основа (`internal/telegram`, бриф B10.3)

Бот публичный — его найдёт кто угодно, — поэтому ничего не построено на доверии к нику: человек привязывается **по числовому идентификатору Telegram**, а попадает внутрь только по приглашению. Без `TELEGRAM_BOT_TOKEN` бота нет вовсе: уведомления для Telegram ждут в outbox, приглашения можно подготовить заранее.

- **Bot API без библиотек** (`api.go`): `getMe`, `sendMessage`, `editMessageText`, `answerCallbackQuery`, `setWebhook` / `deleteWebhook` / `getUpdates`, `setMyCommands`. Адрес запроса содержит токен, а `net/http` цитирует адрес в ошибках — поэтому **каждая ошибка переписывается, и токен не попадает ни в лог, ни на экран** (покрыто тестом). Сообщения — HTML, всё чужое проходит через `Escape`, предпросмотр ссылок выключен. `429` несёт паузу, о которой просит Telegram; «бот заблокирован» отличается от временной ошибки.
- **Приглашения** (`access.go`): одноразовый код на 96 бит, живёт 24 часа, в базе — только SHA-256 от него, сам код виден один раз тому, кто его создал. `UPDATE … WHERE used_at IS NULL` — из восьми одновременных попыток с одним кодом проходит одна. Роли: `owner` (управляет доступом) и `member`. Новое приглашение для уже известного человека меняет роль или возвращает отключённый доступ — владелец сам его отправил. Последнего владельца отключить нельзя.
- **Отзыв доступа действует сразу:** бот спрашивает базу о человеке на каждое обновление и на каждое нажатие кнопки. Отключённый становится посторонним.
- **Посторонние** получают приветствие на языке своего Telegram (ru / uk / en) со ссылкой на форму — не чаще раза в 10 минут; команды, кнопки и всё остальное остаются без ответа. Подбор кодов: 5 попыток в час, дальше тишина. В группах бот молчит даже с владельцем: карточка заявки там была бы показана всем.
- **Получение обновлений** (`runner.go`): **webhook** через nginx — адрес заканчивается секретом, Telegram подтверждает себя заголовком `X-Telegram-Bot-Api-Secret-Token`; оба секрета выводятся из `APP_SECRET` (HMAC), настраивать нечего. Неверный адрес — обычный 404, неверный заголовок — 403, повтор доставки (Telegram повторяет то, что считает недоставленным) не обрабатывается дважды, нечитаемое тело подтверждается, чтобы его не слали сутками. **Long polling** (`TELEGRAM_MODE=polling`) — запасной вариант и режим для машины разработчика. Обновления обрабатываются по одному, в порядке прихода. Если Telegram недоступен при старте — повторы с растущей паузой, остальной сайт это не задевает.
- **Команды владельца:** `/invite` (`/invite owner`), `/users` — список с кнопками «Отключить» / «Вернуть доступ». То же — на странице **«Бот»** в админке (состояние подключения, участники, приглашения с отзывом) и в `krokosha-cli bot check | invite [--owner] | users | disable ID | enable ID`. Все три пути ведут в один `telegram.Access`; всё пишется в журнал действий (`bot.invite`, `bot.join`, `bot.disable`, `bot.enable`).
- Тесты идут против притворного Bot API (`internal/telegram/tgtest`): он принимает вызовы, запоминает их, отказывает по требованию и раздаёт обновления для long polling.


### Telegram-бот: карточки заявок (`internal/telegram/cards.go`, `dialogs.go`, бриф B10.4)

- **Доставка через outbox.** Задача `lead.notify` канала `telegram` рассылает карточку всем, у кого есть доступ. Кому карточка уже ушла — записано в `bot_messages`, поэтому повтор после сбоя Telegram доходит только до тех, кого пропустил, и дублей нет. Человек, заблокировавший бота, остальных не задерживает. Если в боте ещё никого нет, задача ждёт, не расходуя попытки (`outbox.NotReady`), а вход первого человека отправляет накопленное сразу (`Worker.Hurry`). Тому, кто включил `/mute`, карточка приходит без звука.
- **Карточка** — как в брифе: номер и направление, имя, контакт (ник Telegram — ссылкой; почту и телефон Telegram делает кликабельными сам), бюджет и сроки, задача (до 700 знаков, остальное — «Полностью»), число файлов, откуда пришёл посетитель и что смотрел, статус с именем взявшего. Всё введённое посетителем экранируется; предпросмотр ссылок выключен.
- **Статус меняется у всех сразу.** Любое изменение заявки — из бота или из админки — проходит через `leads.Store`, тот зовёт `OnChange`, бот перерисовывает карточку в каждом чате. Кнопки соответствуют статусу: у новой — «Взять в работу», у взятой — «Завершить», у закрытой — «Вернуть в работу».
- **«Взять» дважды нельзя:** первый получает «заявка ваша», второй — окно «уже взял(а) Денис», где бы ни нажал первый — в боте или в админке.
- **Ответ клиенту:** шаблоны на языке клиента → предпросмотр → «Отправить» / «Изменить» / «Отмена»; свой текст — через поле ответа (ForceReply). Отправка — тот же `Store.Reply`, что в админке: сообщение и задача outbox в одной транзакции, заявка переходит в «Ждём клиента». Клиенту с телефоном ничего не отправляется — записывается итог звонка. Один черновик нельзя отправить дважды.
- **Отклонение:** причина (три быстрые, «это спам» — только для новой заявки, или своя) → вежливое письмо из шаблона с предпросмотром либо «Закрыть молча». Если заявку тем временем изменили в админке — отказ не проходит, карточка обновляется.
- **Заметка**, **«Полностью»** (длинный текст приходит частями по границам строк), **«История»** (сообщения, заметки, смены статуса, отметки доставки).
- **Диалоги** (бот ждёт текст ответа, заметки или причины) хранятся у человека в `bot_users.state` и живут два часа: текст, набранный назавтра, не станет заметкой к забытой заявке. `/cancel` — отмена.
- **Стирание.** Всё, что бот написал о заявке (карточки, полные тексты, истории, предпросмотры), запоминается в `bot_messages` — без внешнего ключа, чтобы строки пережили заявку. Перед удалением данных клиента или обезличиванием `Store.OnErase` помечает их, и бот заменяет каждое сообщение строкой «данные клиента удалены». Telegram недоступен — удаление на сервере не ждёт, стирание повторяется, пока не получится (до месяца); сообщение, которое человек удалил сам, считается стёртым.

### Telegram-бот: клиенты, команды, напоминания (`internal/telegram/clients.go`, `commands.go`, `reminders.go`, бриф B10.4–B10.5)

- **Клиент приходит сам** — бот не может написать человеку первым. Кнопка «Продолжить в Telegram» на странице «спасибо» и в письме-подтверждении ведёт на `t.me/<бот>?start=c_<токен заявки>`; ссылка появляется, только пока бот подключён. **Одна заявка — один аккаунт Telegram:** тот же человек может открыть ссылку снова, другой аккаунт получает отказ. Неверная ссылка, заявка робота или обезличенная заявка — человек остаётся прохожим и ничего не узнаёт.
- **Ретранслятор.** Текст клиента (`Store.ClientMessage`) попадает в переписку заявки; заявка, ждавшая клиента, возвращается в работу; всем участникам уходит push — ответом на карточку заявки в их чате, с кнопками «Ответить» и «Карточка» (и письмо владельцу в ту же цепочку, что уведомление о заявке). Ответ сотрудника уходит клиенту от имени бота. Клиент видит только номер и публичный статус своей заявки («принята / в работе / завершена»), на его языке; любые команды дают ему тот же ответ, кнопки карточек — «нет доступа». Лимит — 20 сообщений в час; пока передаётся только текст.
- **Ответ идёт тем путём, которым клиент написал последним** (`Card.ReplyVia`): оставил почту, но продолжил в Telegram — ответ придёт в Telegram; подсказки в боте и в админке говорят то же. Ответ, написанный до прихода клиента в бот, ждёт (`outbox.NotReady`) и уходит сразу после перехода по ссылке. Клиент заблокировал бота — ответ помечается «не доставлено», повторов нет.
- **Команды:** `/leads` — открытые заявки с фильтрами «новые / мои / ждут клиента» (кнопки перерисовывают то же сообщение), `/lead K-0042` — карточка по номеру (она тоже следит за заявкой), `/search текст`, `/stats` — неделя в цифрах (заявки, исходы, доля дошедших до работы, медиана первой реакции, источники), `/mute 2h` / `/mute off`. **В списках нет имён клиентов:** список не принадлежит одной заявке, стереть его при удалении данных нельзя — кто это, говорит карточка, а она стирается.
- **Напоминание:** новая заявка, которую никто не взял за `TELEGRAM_REMIND_MINUTES` (30), пушится ещё раз — один раз на заявку (отметка в истории). Пока в боте никого нет, напоминание не «сгорает».
- **Утренний дайджест** в `TELEGRAM_DIGEST_AT` (09:00) по часам владельца: сколько новых, в работе и ждут клиента, список с кнопками. Раз в день (состояние — в `app_meta`), в пустое утро не приходит, после простоя сервера не приходит посреди дня.

### Трафик сервера (`internal/nginxlog`, бриф B6)

Всё, что отдал nginx, — включая ботов и посетителей без JavaScript, которых статистика сайта не видит.

- **Источник** — JSON access-лог (`KROKOSHA_ACCESS_LOG`, по умолчанию `/var/log/krokosha/nginx-access.json.log`). Сервис читает его раз в 10 секунд с места, где остановился. Файл узнаётся по отпечатку первой строки, а не по inode: это переживает перезапуск, ротацию (`logrotate` → хвост старого файла дочитывается из `.1`), усечение и переезд на другой сервер. Позиция сохраняется в той же транзакции, что и суммы: ни одна строка не теряется и не считается дважды.
- **Хранятся только суммы:** запросы, байты, коды ответов, 404 и гистограмма времени ответа — по минутам (p50 и p95 считаются за любой период сложением корзин); топ адресов по дням (без query-строки, не больше 2000 разных в день — остальное складывается в «прочие адреса», сканер не раздует таблицу); семейства клиентов («Googlebot», «Chrome», «curl») — без самих User-Agent; сканеры — что искали (`/wp-admin`, `.env`, `.git`…) и из какой сети (усечённой).
- **Разные клиенты за час** считаются HyperLogLog в Redis (в нём остаются регистры оценки, а не адреса), без Redis — множеством в памяти. Это цвет «боты» на таймлайне обзора.
- Админка в эту статистику не попадает: nginx пишет её запросы в отдельный лог.

### Статус системы (`internal/sysstatus`)

Последняя сборка сайта (отчёт `status/sync.json`, который оставляет `build-release.sh`: успех, шаг, на котором остановилась, ответил ли GitHub), живой релиз, свежесть данных GitHub, сертификат — тот, что nginx отдаёт посетителям прямо сейчас (сервис спрашивает его по TLS, доступа к `/etc/letsencrypt` у него нет), нагрузка, память, swap, диски, MySQL, Redis, чтение лога, очередь уведомлений, чтение почтового ящика, последняя резервная копия и слежение за сертификатами (отчёты `status/backup.json` и `status/certwatch.json`, которые оставляют `deploy/backup.sh` и `krokosha-certwatch`), база GeoIP. Сверху — список того, на что стоит посмотреть: неудачная сборка, сертификат истекает меньше чем через 14 дней, диск заполнен на 80 %, копия не делалась двое суток, письма без заявки и так далее; экран открывается, даже когда сломано всё остальное.

### Оповещения владельца (`internal/outbox/alert.go`, `krokosha-cli alert`)

`sudo krokosha-cli alert --subject "Что случилось" [--key ПОВОД] < подробности` ставит в `outbox` письмо на `MAIL_NOTIFY_TO` и сообщение владельцам бота — тем же механизмом с повторами, что и уведомления о заявках. Один повод (`--key`, по умолчанию тема и сегодняшняя дата) — одно оповещение по каждому каналу; пока у бота нет владельца, сообщение ждёт его. Пользуются этим скрипты сервера: `backup.sh` (копия не сделана), `krokosha-certwatch` (сертификат не продлевается). Подробности — [deploy/README.md](../deploy/README.md).

**«Пересобрать сейчас»:** веб-сервис ничего запускать не вправе. Он кладёт файл в `/var/lib/krokosha/requests/` — единственный каталог, куда ему разрешено писать; `krokosha-rebuild.path` замечает файл и запускает тот же `krokosha-sync.service`, что и таймер. Без sudo, polkit и D-Bus.

### Ачивки, скидки, личный кабинет (`internal/achievements`, `internal/loyalty`, `internal/clients`, контракт v1.9)

- **Ачивки пасхалок** (`internal/achievements`): `POST /api/eggs/<id>` — квитанция находки, подписанная `APP_SECRET`; `POST /api/eggs/all` с квитанциями восьми пасхалок — квитанция «все пасхалки», по ней форма даёт разовую скидку (использованная помечается отпечатком в `leads.eggs_receipt`); `POST /api/eggs/hello` — браузер учтён как игрок, с первой находкой; `GET /api/eggs` — доли игроков, пересчёт раз в 5 минут в `achievements` из дневных сумм `achievement_daily`, показываются от 10 игроков. Роботы, cookie владельца, `DNT: 1` и `Sec-GPC: 1` получают квитанции, но не считаются.
- **Скидки** (`internal/loyalty`, `content/site.yaml → loyalty`, подхватывается без перезапуска): первая заявка, все пасхалки (разово), уровень по числу выполненных заказов или их сумме, персональная; действует наибольшая, фиксируется в заявке при её создании (`leads.discount_*`). `POST /api/leads/offer` — какой будет скидка, до отправки. Сумму заказа и скидку вручную владелец задаёт в карточке заявки.
- **Личный кабинет** (`internal/clients`): вход по коду (почта или бот; `__Host-kl` привязывает код к браузеру), сессия `__Host-kc`, CSRF в заголовке, заявки и обращения клиента с перепиской, контакты и соцсети, профиль, устройства, удаление; раз в сутки чистятся сеансы, коды и кабинеты без заявок старше срока хранения. Ачивки за заказы (`orders.go`) выдаются при каждом изменении заявки и при открытии кабинета. Админка: «Клиенты» (карточка с контактами, скидкой, ссылкой для входа, слиянием, удалением), «Ачивки» (редкость и проверка уведомлений), «Почта» (`internal/mailboxes` — запросы к `krokosha-mailbox apply`).

## `krokosha-cli admin`

```bash
sudo krokosha-cli admin list                  # учётные записи: состояние, 2FA, последний вход
sudo krokosha-cli admin create LOGIN          # спросит пароль дважды, без эха
sudo krokosha-cli admin passwd LOGIN          # новый пароль, все сеансы учётной записи завершаются
sudo krokosha-cli admin disable|enable LOGIN
sudo krokosha-cli admin totp-reset LOGIN      # потерян телефон
```

Настройки берутся из `/etc/krokosha/env` (`--env-file` — другой файл). Для автоматизации пароль читается из stdin: `--password-stdin`.

## `krokosha-cli indexnow`

```bash
krokosha-cli indexnow --release DIR [--previous DIR] [--all]
```

Читает `sitemap.xml` релиза, сравнивает страницы с предыдущим релизом байт в байт (сборка воспроизводима) и сообщает изменившиеся на `INDEXNOW_API` (по умолчанию `https://api.indexnow.org/indexnow`) с ключом `INDEXNOW_KEY`, который сайт отдаёт как `/<ключ>.txt`. Ничего не изменилось — ничего не отправляется. Вызывается из `deploy/bin/build-release.sh` после каждого релиза с окружением `krokosha-sync.service`; отказ там не фатален — следующий релиз расскажет снова (`internal/indexnow`).

## `krokosha-cli netmap`

Карта интернета страницы `/map` ([docs/netmap.md](../docs/netmap.md)), пакет `internal/netmap`:

```bash
krokosha-cli netmap sync                        # ночная работа (krokosha-netmap.timer): источники → модель → изменения в MySQL → обзор
krokosha-cli netmap fetch|build                 # то же по частям, без MySQL
krokosha-cli netmap route [flags] FROM TO       # маршрут в терминале
krokosha-cli netmap trace TO                    # путь с этого сервера, хоп за хопом (UDP-зонды, без привилегий)
krokosha-cli netmap serve --me IP               # /api/net/* без остального API — для работы над страницей
```

API отвечает на `GET /api/net/route`, `/api/net/trace` (путь, измеренный с сервера: `internal/trace`), `/api/net/as/{asn}`, `/api/net/search`, `/api/net/me` (лимиты — в Redis, маршруты и замеры кэшируются там же на 10 минут) и раз в 30 секунд проверяет `netmap_sync`: появилась новая удачная карта — загружает её из MySQL (~1,4 с) и подменяет старую.

## `krokosha-cli sync`

Пишет в `content/generated/`:

| Файл | Что это |
|---|---|
| `github.json` | `{ public: [...], syncedAt, stale }` — публичные репозитории с уровнем подачи (`tier`), формат — [contract.md §2.3, §5](../docs/contract.md). Схему проверяет сборка сайта (`web/src/lib/schema.ts`) |
| `avatar.<png\|jpg\|gif\|webp>` | аватар с GitHub как есть; в AVIF/WebP его превращает сборка |
| `.cache/` | последний ответ GitHub (`state.json`) и HTTP-кэш с ETag |

Как устроено (`internal/githubsync`):

- **fetch** — сеть: список репозиториев (условный запрос с ETag), затем по три запроса на репозиторий — README, число коммитов и релизов. Метрики кэшируются, пока у репозитория не изменились `pushed_at` / `updated_at` (и не старше 7 дней), поэтому обычный запуск — один запрос.
- **rank** — чистая функция: баллы и уровни по формуле контракта, `pinned` / `exclude` / `overrides` из `content/projects.yaml`. Работает и без сети — правка YAML применяется, даже когда GitHub недоступен.
- **Отказоустойчивость:** GitHub недоступен или кончился лимит → берётся кэш, сайт собирается как обычно. `stale: true` выставляется, только если удачного ответа не было больше 24 часов. Нет ни ответа, ни кэша → код возврата 1, `github.json` не пишется, сборка берёт снимок из `mock/`.
- **Защита сборки:** всё, что сайт отклонил бы (ссылка не `http(s)`, битая картинка аватара, репозиторий без даты), отсекается здесь — один странный репозиторий не должен останавливать релизы.
- Приватные репозитории не запрашиваются вовсе: `GET /users/{user}/repos` отдаёт только публичные, каким бы ни был токен.

Золотой тест `TestRankMatchesContractMock` сверяет ранжирование со снимком GitHub от 2026-09-18, из которого сделан `mock/` — Go и мок не могут разойтись.
