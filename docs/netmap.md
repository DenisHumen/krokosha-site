# Карта интернета (`/map`)

Страница со всеми сетями интернета (автономными системами, AS) и связями между ними. Введите два адреса — карта нарисует, как между ними вероятнее всего пойдут пакеты: сеть за сетью, где сети встречаются (точка обмена трафиком или дата-центр), какие у них там порты и сколько займёт дорога.

Три вида с плавным переходом между ними:

- **карта** — точечная карта мира в стиле сайта (проекция Equal Earth);
- **ядро** — как у CAIDA: крупнейшие сети в центре, мелкие по краю, угол — долгота сети;
- **глобус** — ортографическая проекция, вращается сама, пока её не трогают.

Разметка и тексты страницы описаны в [contract.md §8](contract.md#8-v16-карта-интернета).

## Как устроено

```
каждую ночь, 02:20–02:40 UTC — krokosha-netmap.timer → krokosha-cli netmap sync
  источники             →  /var/lib/krokosha/netmap/          как есть; не скачался — вчерашний
  модель                →  MySQL, таблицы netmap_*            только то, что изменилось
  обзор для страницы    →  /var/www/krokosha/netmap/          overview-<хэш>.bin (+ .gz) и overview.json
                                                             (nginx отдаёт как /netmap/data/)
API (krokosha-api)
  раз в 30 с смотрит netmap_sync; новая карта — загрузить из MySQL, подменить старую
  модель в памяти  →  /api/net/route, /api/net/as/{asn}, /api/net/search, /api/net/me

браузер
  /netmap/land.bin + /netmap/data/overview.json → overview-<хэш>.bin → WebGL
  форма маршрута → /api/net/route → таблица + анимация пути
```

### Модель (`api/internal/netmap`)

| Файл | Что делает |
|---|---|
| `link.go`, `asn.go` | связь двух AS, её вид и откуда она известна; разбор файла CAIDA |
| `mrt.go` | чтение снимков RouteViews (MRT TABLE_DUMP_V2, в том числе ADD-PATH): пути AS, из них — связи |
| `prefix.go` | диапазоны адресов → AS (двоичный поиск), имена и страны AS из iptoasn |
| `peeringdb.go` | загрузка PeeringDB (по объекту на файл, пауза между запросами) и чтение |
| `model.go` | граф связей (CSR), конусы клиентов, ранги, точки обмена и дата-центры |
| `place.go` | где сеть на карте: по её адресам (GeoIP), иначе по её дата-центрам, иначе рядом с соседями |
| `route.go` | маршрут и где сети встречаются |
| `overview.go` | обзор для браузера (формат `KNM1`) |
| `sources.go` | скачивание и чтение всех источников |
| `store.go` | карта в MySQL: запись только изменений, восстановление модели, запуски синхронизации |
| `watch.go` | API: загрузка новой карты после каждой синхронизации |
| `http.go` | API |
| `trace_http.go` | API: замер пути с сервера сайта |

**Связи.** Основа — CAIDA, где у каждой связи есть вид. Связи из свежих таблиц RouteViews, которых у CAIDA нет, добавляются с видом «неизвестно». Путь AS с AS_SET, конфедерациями, частными номерами или петлёй обрывается на первом таком месте; повторы одной AS (prepend) схлопываются.

**Маршрут.** Для каждой AS назначения строится дерево лучших путей до неё (очередь по корзинам, как у Дейкстры), с правилами экспорта BGP: путь, полученный от провайдера или пира, дальше отдаётся только клиентам. Оценка пути — `2 × длина + штраф`, где шаг к клиенту стоит 0, к пиру 1, к провайдеру 2. Чистая модель Гао–Рексфорд не подошла: утёкшие «клиентские» связи в данных тянули маршруты через полмира. При равенстве предпочтение — сеть с бо́льшим конусом.

**Где сети встречаются.** Общая точка обмена или общий дата-центр из PeeringDB, если крюк от текущего места не больше 1 500 км. Иначе — догадка: клиент встречает провайдера «здесь», провайдер клиента — у клиента дома, пиры — здесь, если другой не совсем мелкий. Скорости портов — из PeeringDB (`netixlan.speed`), только для точек обмена.

**Anycast.** Адреса известных anycast-резолверов (Cloudflare, Google, Quad9, OpenDNS) не имеют одного места: конец маршрута — ближайшее к отправителю (не дальше 3 000 км) присутствие сети назначения.

**Задержка** — оценка, не замер: `RTT ≈ 2 × 1,3 × расстояние / 200 км/мс + 0,2 мс на каждую сеть`. Свет в волокне проходит около 200 км за миллисекунду, кабели длиннее прямой примерно на треть. **Потери** можно только измерить — до этапа C в таблице «не измерено».

### Обзор (`KNM1`)

Little-endian, секции выровнены на 4 байта, чтобы браузер читал их типизированными массивами без копирования. Сети отсортированы по рангу (крупнейшие первыми), и ядро и имена — это первые N из них.

| Часть | Содержимое |
|---|---|
| заголовок, 16 × u32 | `"KNM1"`, версия, время сборки (unix), число сетей на карте, точек обмена, пучков, связей ядра, сетей в ядре, сетей с именами, всего связей, всего сетей, диапазонов IPv4, IPv6, длина текста, 0, 0 |
| сети | `asn u32[]`, `lat i16[]`, `lon i16[]` (сотые градуса), `size u8[]` (разрядность конуса), `degree u8[]`, `type u8[]`, `country u8[]` |
| точки обмена | `lat i16[]`, `lon i16[]`, `members u16[]`, `capacity u32[]` (Гбит/с) |
| пучки | связи между клетками 2° × 2°, 5 000 крупнейших: `lat1, lon1, lat2, lon2 i16[]`, `links u32[]` |
| ядро | связи между 1 000 крупнейших сетей: `a u16[]`, `b u16[]`, `rel i8[]` |
| текст | JSON: `countries[]`, `names[]` (3 000 крупнейших), `exchanges[[name, city, country]]`, `types[]` |

Файл называется по хэшу содержимого и кэшируется надолго; `overview.json` (манифест) — коротко. Сборка оставляет три последних файла, чтобы страница, открытая до обновления, догрузилась.

Обе стороны формата проверяются на одном файле: Go-тест `TestOverviewGolden` пишет обзор тестового мира в `web/tests/fixtures/netmap-overview.bin`, а тесты страницы читают его своим декодером.

### Страница (`web/src/scripts/netmap/`)

| Файл | Что делает |
|---|---|
| `data.ts` | чтение `KNM1` и `KLD1` |
| `projection.ts` | Equal Earth, ядро, ортографическая проекция; камера |
| `renderer.ts` | WebGL 1 без библиотек: один вершинный шейдер ставит точку в два вида и смешивает их — так работает переход между видами |
| `layers.ts` | слои: суша, сети, точки обмена, пучки, ядро, связи выбранной сети, след маршрута |
| `panel.ts` | таблица маршрута и карточка сети — только `textContent`: имена сетей приходят из реестров, за них никто не ручается |
| `map.ts` | загрузка, мышь, касания, клавиатура, форма, адрес страницы |

Без WebGL видна причина, а форма и таблица маршрута работают. При `prefers-reduced-motion` переходы и анимация пакета не играют.

## API

| Запрос | Ответ | Лимит в минуту | Кэш |
|---|---|---|---|
| `GET /api/net/route?from=&to=` | маршрут | 30 | 10 мин |
| `GET /api/net/as/{asn}` | сеть: размер, соседи (до 16 каждого вида), точки обмена | 60 | 1 ч |
| `GET /api/net/search?q=` | до 12 сетей по номеру или имени | 60 | 1 ч |
| `GET /api/net/me` | адрес посетителя, его сеть и место | 30 | `no-store` |
| `GET /api/net/trace?to=` | путь, измеренный с сервера сайта (ниже) | 3, и 2 одновременно на сервер | 10 мин |

Ошибки — `{"error": "<код>"}`: `bad_address`, `private_address` (частные сети, CGNAT, документационные и служебные диапазоны), `not_routed`, `no_path`, `unknown_as`, `busy` (429), `not_ready` (503 — модель ещё не построена), `trace_failed` (502 — замер не удался).

## Замер с сервера сайта

Маршрут модели — то, что вероятно. По кнопке «Измерить с сервера сайта» сервер отправляет к адресу настоящие зонды и показывает, как пакеты прошли на самом деле (`internal/trace`, `GET /api/net/trace`):

- **Хопы** — UDP-датаграммы с растущим TTL, как у `tracepath`: по три на каждый TTL до 30, раундами с паузой 120 мс (роутер, который отвечает раз в секунду, всё равно ответит на часть). Ответ ICMP «время жизни истекло» ядро кладёт в очередь ошибок сокета (`IP_RECVERR`), поэтому **привилегии не нужны** — ни root, ни `CAP_NET_RAW`, ни изменений системы. Каждый зонд идёт на свой порт: многие роутеры цитируют только UDP-заголовок, и по порту видно, на какой зонд пришёл ответ, а значит, и время. Сам адрес отвечает «порт недоступен» — там путь кончается.
- **Время до самого адреса** — TCP-рукопожатия с портом 443, потом 80 (пять попыток): многие хосты молчат на UDP-зонды, а веб-сервер отвечает на рукопожатие; отказ (RST) — тоже ответ.
- **Каждый хоп** — адрес, обратный DNS, сеть (по диапазонам адресов), и если адрес в пиринговой сети точки обмена — точка обмена и **сеть, чей это порт** (адреса портов из PeeringDB, таблица `netmap_ixaddr`), место на карте (порт точки обмена — там, где точка обмена, остальное — по GeoIP), сколько зондов ответило и за сколько.
- На карте измеренный путь рисуется цветом «ok» и начинается на сервере сайта; переключатель над таблицами меняет, какой путь на карте — модели или измеренный.

Это путь **от сервера сайта**, а не от посетителя. Роутеры отвечают на зонды, когда у них есть время: хоп, пропустивший часть, ещё не доказывает потерь — доказывают ответы самого адреса.

Ограничения: 3 замера в минуту с одного посетителя, 2 одновременно на весь сервер, частные и служебные адреса не меряются; результат для адреса хранится в Redis 10 минут и одинаков для всех. Замер — около 100 UDP-пакетов и до 10 TCP-рукопожатий за 3–5 секунд. `krokosha-cli netmap trace АДРЕС` делает то же в терминале.

**Приватность.** `/api/net/me` возвращает посетителю его собственный адрес и ничего не сохраняет. API не записывает адреса из формы, а nginx для `/api/net/` пишет в журнал только путь — без строки `?from=&to=` и без referer (формат `krokosha_json_path`). Маршрут хранится в Redis 10 минут под ключом из двух адресов — это кэш, не журнал. Ссылка на маршрут хранит `from=me` вместо адреса, так что, поделившись ею, человек не раскрывает свой IP.

## Хранение и обновление

`krokosha-cli netmap sync` (`krokosha-netmap.service`, раз в сутки):

1. Скачивает источники: CAIDA — только когда вышел новый месяц, таблицы RouteViews — полуночные (до их выхода — вчерашние), iptoasn и PeeringDB — свежие. Что не скачалось, берётся с прошлого раза.
2. Строит модель (см. выше) и пишет обзор под новым именем — страница его ещё не видит.
3. Сравнивает модель с таблицами и записывает только разницу. Сеть или связь, которой больше нет, не удаляется, а помечается `gone_at`; вернувшаяся снимает пометку и сохраняет `first_seen` — день, когда её увидели впервые. Появления, исчезновения и смены вида связи перечислены в `netmap_change`. Через 90 дней ушедшее и журнал забываются.
4. Переключает `overview.json` на новый обзор и отмечает запуск в `netmap_sync`: сколько сетей, связей, адресов, что появилось, ушло, изменилось.

Защита: если новая карта меньше хранимой больше чем на 15 % (по связям, сетям или адресам) — например, источник пришёл обрезанным, — она не записывается. На сайте остаётся прежняя, экран «Статус системы» говорит почему. Настоящее уменьшение записывается с `--force`. Два запуска сразу не идут: их разводит именованная блокировка MySQL.

| Таблица | Строк | Что |
|---|---|---|
| `netmap_sync` | по запуску | когда, чем кончился, счётчики, отчёт источников, ошибка |
| `netmap_as` | ~90 000 | сеть: имя, страна, тип, место на карте и как оно найдено; `first_seen`, `gone_at` |
| `netmap_link` | ~700 000 | связь двух сетей: вид, где увидена; `first_seen`, `gone_at` |
| `netmap_change` | за 90 дней | что появилось, ушло, сменило вид |
| `netmap_prefix` | ~580 000 | диапазоны адресов → сеть (4 или 16 байт адреса) |
| `netmap_ix`, `netmap_facility` | ~1 300, ~6 000 | точки обмена и дата-центры с местом на карте |
| `netmap_port`, `netmap_site`, `netmap_lan` | ~55 000, ~59 000, ~2 600 | порты сетей на точках обмена, присутствие в дата-центрах, пиринговые сети точек обмена |
| `netmap_ixaddr` | ~90 000 | адреса портов сетей в пиринговых сетях — чей роутер ответил на замере |

API загружает карту новейшего удачного запуска (`netmap.Load`) и восстанавливает ту же модель, что построил sync: тест сравнивает их до байта обзора. Координаты хранятся в `DOUBLE`: `FLOAT` через текстовый протокол MySQL возвращается с шестью знаками, и тогда каждую ночь «менялись» бы все сети. Пока загружается новая карта, отвечает старая.

## Разработка

```bash
cd api
go run ./cmd/krokosha-cli netmap fetch --data /tmp/netmap/data
go run ./cmd/krokosha-cli netmap build --data /tmp/netmap/data --geoip /path/to/dbip-city-lite.mmdb --out /tmp/netmap/out
go run ./cmd/krokosha-cli netmap route --data /tmp/netmap/data --geoip ... 1.1.1.1 46.175.147.165
go run ./cmd/krokosha-cli netmap serve --data /tmp/netmap/data --geoip ... --out /tmp/netmap/out --me 95.46.140.1
```

Флаги — до адресов. `serve` заменяет API на время разработки (`127.0.0.1:8091`); `--me` — какой адрес считать адресом посетителя. `sync` работает с MySQL из `--env-file`; с `--no-fetch` (или `NETMAP_FETCH=off`) ничего не скачивает. Страница с ним:

```bash
NETMAP_DEV_API=http://127.0.0.1:8091 npm --prefix web run dev
```

С `NETMAP_DEV_API` dev-сервер Astro проксирует `/api/net` и `/netmap/data` и не требует `/` в конце адресов.

Тесты: `go test ./internal/netmap` (с `-update` — переписать обзор тестового мира для тестов страницы; хранение — с `KROKOSHA_TEST_MYSQL`, см. `api/compose.test.yaml`), `npm test` (`tests/unit/netmap.test.ts`), `npx playwright test tests/e2e/map.spec.ts`. Установщик в CI строит карту из маленького мира `api/internal/netmap/testdata/world` (`--netmap-offline`): тем же юнитом, что ночью, с проверкой таблиц, nginx, API и журнала.
