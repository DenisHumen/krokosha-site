# deploy/ — установка и эксплуатация на VPS

**Статус:** устанавливаются сайт (nginx, сертификат, сборка релизов по таймеру), MySQL и Redis в Docker, API с формой заявок, админка с первым администратором (статистика, трафик, статус системы, заявки, бот), Telegram-бот (токен — `--telegram-token-file` или вопрос без эха; проверяется через `getMe`; в конце установки печатается одноразовая ссылка для владельца), почтовый сервер (ящики, DKIM, список DNS-записей в конце установки), фаервол, fail2ban, ночные резервные копии с восстановлением, слежение за сертификатами с оповещением владельца, гео по IP (DB-IP City Lite или GeoLite2), IndexNow ([docs/roadmap.md](../docs/roadmap.md)).

> На VPS пока ничего не выкладывается — проверяем на локальном стенде (ниже).

## Установка на чистый сервер

Ubuntu 24.04 (или Debian 12), домен уже указывает на сервер:

```bash
git clone https://github.com/DenisHumen/krokosha-site.git
sudo ./krokosha-site/deploy/install.sh --domain example.com --email admin@example.com
```

Скрипт спросит согласие с условиями Let's Encrypt (или `--agree-tos`), затем логин и пароль первого администратора (пароль — без эха, дважды, не короче 12 символов). В конце печатает адрес админки — он секретный, сохраните его. Повторный запуск ничего не ломает: он приводит сервер к тому же состоянию. Все параметры — `install.sh --help`.

| Что | Где |
|---|---|
| Код | `/opt/krokosha/repo` (клон репозитория), бинарники — `/opt/krokosha/bin` |

| **Данные** | `/srv/krokosha` (`--data-dir`): `mysql/`, `redis/`, `mail/`, `attachments/`, `backups/`, `config/`. **Переезд = скопировать эту директорию** ([architecture.md §6](../docs/architecture.md)) |
| Настройки и секреты | `/etc/krokosha` — ссылка на `/srv/krokosha/config`. `env` — `600 root`, описание в [`env/.env.example`](env/.env.example); пароль root MySQL лежит отдельно (`mysql-root.env`), API его не видит |

| Кэши | `/var/lib/krokosha` — npm, Go, ответы GitHub; можно удалить без потерь |
| Логи | `journalctl -u krokosha-sync.service`, `/var/log/krokosha/` (JSON access-лог сайта и отдельный — админки, 30 дней). Access-лог сайта читает API (группа `adm`) для экрана «Трафик сервера» |
| Состояние | `/var/lib/krokosha/status/` — отчёты для экрана «Статус системы»: `sync.json` (последняя сборка), `backup.json` (последняя копия), `certwatch.json` (сертификаты); `/var/lib/krokosha/requests/` — сюда админка кладёт запрос «пересобрать сейчас» |
| Резервные копии | `/srv/krokosha/backups/<дата-время>/`, `latest` → последняя; каждую ночь в 03:30 (`krokosha-backup.timer`). См. «Резервные копии» ниже |

Какую читает API — `GEOIP_DB` |
| Пользователь | `krokosha` — системный, без шелла и пароля; от него идут sync и сборка |

## Локальный стенд

Контейнер Docker, который выглядит как VPS (Ubuntu 24.04, systemd); внутри отрабатывает настоящий `install.sh`, включая Docker с MySQL и Redis.

```bash
deploy/docker/staging/staging.sh up       # установить текущую ветку (закоммиченное состояние) → https://krokosha.localhost
deploy/docker/staging/staging.sh update   # подтянуть новые коммиты ветки и применить (update.sh)
deploy/docker/staging/staging.sh test     # полный цикл, как в CI: установка, повтор, update, откат, удаление (~2,5 мин)
deploy/docker/staging/staging.sh shell    # root-консоль внутри
deploy/docker/staging/staging.sh down     # убрать стенд
```

Нужен Docker (на Windows — Docker Desktop, запускать из Git Bash или WSL). Сертификат самоподписанный: браузер предупредит один раз. WireGuard в ядре WSL2 отсутствует, поэтому эта часть проверки выполняется только в CI.

Админка стенда — `https://krokosha.localhost/_staging/`, логин `dev`; пароль случайный, `staging.sh up` печатает его в конце.

## Обслуживание

```bash
sudo /opt/krokosha/repo/deploy/update.sh              # подтянуть main и применить: код, конфиги, сборка, релиз
sudo systemctl start krokosha-sync.service            # пересобрать сейчас (само — каждые 6 часов)
sudo /opt/krokosha/repo/deploy/rollback.sh            # вернуть предыдущий релиз (--list — показать все)
sudo /opt/krokosha/repo/deploy/uninstall.sh           # удалить сайт с сервера; данные в /srv/krokosha остаются (--purge удаляет и их)
sudo /opt/krokosha/repo/deploy/backup.sh              # резервная копия сейчас (сама — каждую ночь)
sudo /opt/krokosha/repo/deploy/restore.sh --from DIR  # восстановить из копии (см. ниже)
```

Сервер сам забирает код из GitHub; ключей от сервера в GitHub нет (бриф B9).

## Резервные копии

Каждую ночь в 03:30 (`krokosha-backup.timer` → [`backup.sh`](backup.sh)) в `/srv/krokosha/backups/<дата-время>/` складываются:

- `mysql.sql.gz` — дамп базы (`mysqldump` из контейнера: заявки, переписка, статистика, учётные записи, журнал);
- `config.tar.gz` — `/srv/krokosha/config`: настройки и секреты (`env`, пароль root MySQL);
- `letsencrypt.tar.gz` — сертификаты, если они от Let's Encrypt;
- `mail/` и `attachments/` — письма, ящики, DKIM-ключ и файлы заявок. Копируются `rsync --link-dest`: файл, который не менялся со вчерашней копии, — **жёсткая ссылка** на вчерашний, поэтому месяц копий занимает место примерно одной;
- `MANIFEST` — что, когда и с какого сервера.

Хранятся 7 последних дневных и 4 недельных (воскресных) — `BACKUP_KEEP_DAILY`, `BACKUP_KEEP_WEEKLY` в `/etc/krokosha/env`. Директория — `700 root`: в копии лежат секреты.

**Копия на другой машине.** Копия рядом с данными спасает от ошибки, но не от умершего диска. `BACKUP_RSYNC_TO=user@host:/path` в `/etc/krokosha/env` — и каждая копия после создания уезжает туда `rsync`-ом по SSH (ключ root, `BatchMode`: пароль спросить некому; на той стороне нужен `rsync`). Пока переменная пуста, установщик и экран «Статус системы» об этом напоминают. Проверить руками: `sudo /opt/krokosha/repo/deploy/backup.sh` — в конце печатает размер и куда скопировано.

**Восстановление** — [`restore.sh`](restore.sh): останавливает API и почту, заменяет базу, письма, файлы и те настройки, которые обязаны остаться прежними (секрет, которым подписаны адреса ответов и ссылки; путь админки; пароль служебного ящика; токен бота; ключи MaxMind и IndexNow; сроки хранения), после чего запускает `install.sh --from-env`, чтобы nginx, почтовый сервер и API всё подхватили. Пароли базы и Redis остаются свои у каждой установки. Без `--yes` просит набрать домен — восстановление **заменяет** то, что есть.

```bash
sudo /opt/krokosha/repo/deploy/restore.sh --from /srv/krokosha/backups/latest
```

Статус последней копии виден на экране «Статус системы»; если копия не сделалась, владелец получает письмо и сообщение в Telegram (один раз в сутки).

### Переезд на другой сервер

1. На старом сервере: `sudo /opt/krokosha/repo/deploy/backup.sh --to /root/move` (или взять `BACKUP_RSYNC_TO`-копию / `/srv/krokosha/backups/latest`) и перенести директорию на новый сервер, например `scp -r`.
2. На новом сервере — обычная установка с тем же доменом, пока DNS ещё смотрит на старый: `sudo ./deploy/install.sh --domain <домен> --email … --tls selfsigned --skip-dns-check --yes --admin-login … --admin-password-file …` (администратор нужен установщику формально — из копии придут настоящие).
3. `sudo /opt/krokosha/repo/deploy/restore.sh --from /root/move/<дата-время>`. Заявки, переписка, письма, ящики с паролями, DKIM-ключ, бот, ключи — всё на месте; в DNS менять нечего, кроме адресов.
4. Переключить в DNS записи `A` домена и `mail` на новый адрес и попросить провайдера поставить **PTR** нового адреса на `mail.<домен>`.
5. Когда DNS обновился: `sudo /opt/krokosha/repo/deploy/install.sh --from-env --tls letsencrypt --agree-tos` — настоящий сертификат. (Если в копии был `letsencrypt.tar.gz`, `restore.sh` уже положил старые сертификаты на место, и продление продолжится само.)
6. Старый сервер: `uninstall.sh --purge`, когда всё проверено.

## Смена домена

Сайт переезжает на новое имя одной командой — когда записи `A` нового домена (`@`, `www`, `mail`) уже указывают на сервер:

```bash
sudo /opt/krokosha/repo/deploy/install.sh --from-env --domain НОВЫЙ-ДОМЕН
```

- **Новый домен — основной.** Сертификат Let's Encrypt на него, `www.` и `mail.`; канонические адреса, sitemap, IndexNow и вебхук Telegram — на новом имени. Админка — по тому же секретному пути, войти заново: cookie сессии привязан к имени.
- **Прежний домен — старое имя** (`OLD_DOMAIN` в настройках). Каждая его страница отвечает постоянным редиректом `301` на ту же страницу нового, по HTTP и по HTTPS — со своим прежним сертификатом, который продлевается, пока имя указывает на сервер.
- **Почта переезжает целиком.** Ящики переименовываются в новый домен вместе с паролями и письмами (`denis@старый` → `denis@новый`), письма на старые адреса — и на адреса ответов по заявкам — приходят в те же ящики. Почтовый сервер называет себя `mail.НОВЫЙ-ДОМЕН`, для нового домена создаётся ключ DKIM и подписываются письма обоих имён. Что внести в DNS нового домена — в конце вывода и в `/srv/krokosha/mail/DNS.txt`. Ключ DKIM можно сделать заранее, чтобы запись была в DNS к моменту переезда: `docker exec krokosha-mail-1 setup config dkim keysize 2048 selector mail domain НОВЫЙ-ДОМЕН` (установщик возьмёт готовый).
- **Руками:** PTR у хостера — на `mail.НОВЫЙ-ДОМЕН`; в почтовых программах — сервер `mail.НОВЫЙ-ДОМЕН` и логин по новому адресу; в Google Search Console — «Изменение адреса» в настройках ресурса старого домена (оба домена подтверждены), в Bing Webmaster Tools — «Site Move».

Старое имя отпускается само: при очередном запуске установщика (`update.sh`), когда оно больше не указывает на этот сервер, пропадают его редирект, почтовые адреса и сертификат. Отпустить сразу: `--old-domain none`.

## Сертификаты и оповещения

Штатное продление — `certbot.timer`. Сверх него раз в сутки в 04:40 [`bin/krokosha-certwatch`](bin/krokosha-certwatch) (`krokosha-certwatch.timer`) смотрит **не на файлы, а на то, что реально отдают** nginx (`:443`) и почтовый сервер (`:993`): продлённый сертификат, который никто не перечитал, ничем не лучше просроченного. Меньше 14 дней (`CERTWATCH_RENEW_BELOW_DAYS`) — тут же `certbot renew`, hook перезагружает nginx и перезапускает почту. Не продлилось — владелец получает письмо и сообщение в Telegram с ответом certbot, на экране «Статус системы» появляется ошибка.

Оповещения — общий механизм: `sudo krokosha-cli alert --subject "…" < подробности` ставит письмо и сообщение в Telegram в очередь `outbox` (доставка с повторами, как у уведомлений о заявках). Один повод — одно оповещение в сутки (`--key`). Им же пользуются `backup.sh` и `krokosha-certwatch`.

## Гео: страны и города посетителей

Страна и город на экранах статистики и в карточках заявок определяются по локальной базе (сеть не спрашивается, адрес не хранится).

**По умолчанию — [DB-IP City Lite](https://db-ip.com/db/download/ip-to-city-lite)**: бесплатно, без аккаунта и ключей. Установщик сам скачивает её (около 60 МБ, на диске 130 МБ) в `/var/lib/GeoIP/dbip-city-lite.mmdb` и включает `krokosha-dbip.timer`. DB-IP выкладывает новую базу 1-го числа каждого месяца, таймер заглядывает раз в день и качает, только когда файла этого месяца ещё нет ([`bin/krokosha-dbip-update`](bin/krokosha-dbip-update): архив проверяется, файл заменяется целиком, старый остаётся, если новый не скачался). Лицензия данных — CC BY 4.0: там, где показываются результаты, нужна ссылка на DB-IP, поэтому внизу каждой страницы админки — «IP Geolocation by DB-IP».

```bash
sudo systemctl start krokosha-dbip.service      # скачать сейчас, если таймер не справился
sudo journalctl -u krokosha-dbip                 # что он делал
```

**GeoLite2 от MaxMind** — вместо неё, по желанию. Тоже бесплатно, но нужен аккаунт: [signup](https://www.maxmind.com/en/geolite2/signup) → в аккаунте «Manage License Keys» → ключ в файл, затем:

```bash
sudo /opt/krokosha/repo/deploy/install.sh --from-env --maxmind-account 123456 --maxmind-key-file /root/maxmind.key
```

Установщик ставит `geoipupdate`, пишет `/etc/GeoIP.conf` (только root), скачивает `GeoLite2-City.mmdb` и включает `krokosha-geoipupdate.timer` (среда и суббота — MaxMind публикует базу по вторникам и пятницам). Как только GeoLite2 на месте, API переходит на неё, а DB-IP и её таймер убираются; пока ключ не принёс первый файл, работает DB-IP. Ссылка внизу админки меняется на строку, которую просит лицензия GeoLite2.

Какую базу читает API, решает установщик через `GEOIP_DB` в `/etc/krokosha/env`: при смене он перезапускает API, а новую версию того же файла API замечает сам. `GEOIP_DB=off` — страны не определяются, оба таймера выключены. Путь к своей базе в формате MaxMind DB установщик оставляет как есть, обновлять её — ваша забота. Экран «Статус системы» показывает, какая база загружена и когда собрана, и предупреждает, если она старше шести недель.

## Карта интернета

Страница `/map` ([docs/netmap.md](../docs/netmap.md)) рисует сети интернета по открытым данным. Каждую ночь в 02:20–02:40 UTC `krokosha-netmap.timer` запускает `krokosha-cli netmap sync`: свежие источники (около 130 МБ) в `/var/lib/krokosha/netmap`, сборка (около минуты одного ядра и до 300 МБ памяти на миг — юнит ограничен `CPUQuota`, `MemoryMax`, `Nice`), в MySQL — только то, что изменилось, обзор для страницы — в `/var/www/krokosha/netmap` (nginx отдаёт его как `/netmap/data/`). API подхватывает новую карту сам за полминуты. Первую карту установщик начинает строить сразу, в фоне — несколько минут; до тех пор страница говорит, что данные не готовы.

```bash
sudo systemctl start krokosha-netmap.service     # построить сейчас (ждёт конца: минуты)
sudo journalctl -u krokosha-netmap               # что было ночью: источники, что появилось и ушло
```

Источник, который не скачался, берётся с прошлого раза. Карта, которая меньше хранимой больше чем на 15 %, не записывается (обрезанный источник не должен «удалить» полинтернета): на сайте остаётся прежняя, «Статус системы» объясняет почему. Если уменьшение настоящее:

```bash
sudo systemd-run --pipe --wait --uid=krokosha --gid=krokosha -p EnvironmentFile=/etc/krokosha/env \
  /opt/krokosha/bin/krokosha-cli netmap sync --force
```

Таблицы карты (`netmap_*`, около 75 МБ) попадают в резервную копию без строк: их построит следующая ночь. В журнал nginx запросы `/api/net/` пишутся без строки запроса — адреса, которые люди прокладывают, там не остаются.

## Поисковики

- **IndexNow** — включён по умолчанию (`--no-indexnow` выключает). Установщик один раз генерирует ключ (`INDEXNOW_KEY`), сайт отдаёт его как `/<ключ>.txt`, а [`build-release.sh`](bin/build-release.sh) после каждого релиза сообщает на `api.indexnow.org`, **какие страницы изменились** (сборка воспроизводима: страница, чьё HTML совпало с прошлым релизом, не менялась). Оттуда узнают Bing (и через его индекс DuckDuckGo, Ecosia и другие), Yandex, Naver, Seznam. Google в IndexNow не участвует.
- **Google Search Console** — один раз руками: [search.google.com/search-console](https://search.google.com/search-console) → «Добавить ресурс» → тип **Домен** (`krokosha.com`) → подтвердить TXT-записью в DNS (или тип «Префикс URL» с HTML-тегом — тег добавляется в `content/site.yaml`, ключ `verification.google`, и попадает в `<head>` при следующей сборке). После подтверждения: «Файлы Sitemap» → `https://krokosha.com/sitemap.xml`. Там же потом видны запросы, позиции и ошибки индексации.
- **Bing Webmaster Tools** — [bing.com/webmasters](https://www.bing.com/webmasters): проще всего «Импортировать из Google Search Console» (даёт доступ к уже подтверждённому ресурсу), иначе — та же TXT-запись или мета-тег (`verification.bing` в `content/site.yaml`). Sitemap туда тоже добавить: `https://krokosha.com/sitemap.xml`. Bing показывает и приём IndexNow («IndexNow» в меню).
- `robots.txt` и `sitemap.xml` собираются сайтом сами; админка в них не упоминается.

## Как устроен релиз

`krokosha-sync.timer` (00:10, 06:10, 12:10, 18:10) → [`bin/build-release.sh`](bin/build-release.sh):

1. `krokosha-cli sync` — данные GitHub. Ошибка не фатальна: сборка идёт из кэша.
2. `npm ci --omit=dev` — только если изменился `package-lock.json`.
3. `astro build` → `check-dist.mjs`. Не прошла проверка — релиз не публикуется, живой сайт не трогается.
4. Копия в `releases/<дата-время>`, атомарная смена симлинка `current`, удаление релизов старше трёх.
5. Отчёт в `status/sync.json` — чем кончилось и на каком шаге остановилось (пишется и при сбое).

Кроме таймера сборку запускает кнопка «Пересобрать сейчас» в админке: `krokosha-rebuild.path` следит за файлом-запросом и стартует тот же юнит. У веб-сервиса нет прав что-либо запускать — только положить этот файл.

npm и сборка запускаются с **чистым окружением**: секреты из `/etc/krokosha/env` (токен GitHub, позже — почта и бот) стороннему коду не видны. Сам юнит изолирован средствами systemd (`ProtectSystem=strict`, без привилегий, лимит памяти), чтобы сборка не мешала остальному на небольшом VPS.

## Nginx

- HTTP → HTTPS, `www` → основной домен, запросы с чужим именем хоста (голый IP, чужой домен) остаются без ответа.
- Страницы — `Cache-Control: no-cache` (новый релиз виден сразу), файлы `/_astro/` с хэшем в имени — год, `immutable`.
- «Страница не найдена» — на языке адреса: `/uk/…` → украинская, `/ru/…` → русская.
- Заголовки безопасности — [`nginx/snippets/krokosha-headers.conf`](nginx/snippets/krokosha-headers.conf). CSP с хэшами скриптов и стилей приходит из сборки (`<meta>`), заголовок добавляет `frame-ancestors`. HSTS — только с настоящим сертификатом.
- gzip и, если в системе есть модуль, brotli.
- Access-лог в JSON — источник для экрана «Трафик сервера» в админке.
- **Админка** проксируется только по HTTPS и только под секретным путём. Её запросы пишутся в отдельный лог (`nginx-admin.json.log`): секретный путь и клики владельца не попадают в статистику трафика. На форму входа — свой лимит: 20 запросов в минуту с адреса (проверка пароля намеренно дорогая).

## Почта

Почтовый сервер — [docker-mailserver](https://docker-mailserver.github.io/docker-mailserver/latest/) 16 в одном контейнере (Postfix, Dovecot, Rspamd; без ClamAV — он один занял бы гигабайт памяти), сервис `mail` в том же [`compose/compose.yaml`](compose/compose.yaml), профиль `mail`. Ставится по умолчанию; `--no-mail` — не ставить (отказ запоминается). Без HTTPS (`--tls none`) почты нет: пароли не должны ходить открытым текстом.

```bash
sudo ./install.sh --domain example.com --email admin@example.com \
  --mailbox denis@example.com --mail-name "Denis Humen"
```

- **Ящики.** Служебный `leads@<домен>` создаётся всегда: от его имени сайт входит на сервер, чтобы отправлять письма (конверт — `leads@`, заголовок `From` — владелец), и в него же возвращаются ответы клиентов; пароль генерируется и лежит в `/etc/krokosha/env`, знать его никому не нужно. Ящик владельца — `--mailbox`: туда приходят уведомления о заявках; пароль спрашивается без эха дважды либо берётся из `--mailbox-password-file`; если спросить некого, ящик не создаётся и установщик говорит, как создать его позже. `postmaster@` и `abuse@` — псевдонимы ящика владельца.
- **Управление ящиками:** `sudo krokosha-mailbox list | add АДРЕС | passwd АДРЕС | del АДРЕС`. Пароль никогда не передаётся аргументом команды (его видели бы все на машине) — только вопросом без эха или `--password-stdin`. В файле ящиков — хэши SHA512-crypt; сервер замечает изменения сам за несколько секунд.
- **Сертификат** — тот же, что у сайта: в него добавляется имя `mail.<домен>` (существующий сертификат Let's Encrypt перевыпускается с `--expand`, если имени в нём ещё нет). После продления hook перезагружает nginx и перезапускает почтовый контейнер.
- **DKIM-ключ** создаётся один раз; открытая часть попадает в список DNS-записей.
- **Данные** — `/srv/krokosha/mail/`: `data/` (письма), `state/` (Rspamd, очереди), `logs/`, `config/` (ящики, псевдонимы, DKIM). Переезжают вместе со всем остальным.
- **Защита:** внутри контейнера работает свой fail2ban (подбор паролей SMTP/IMAP); ящик может отправлять только от своего имени (`SPOOF_PROTECTION`); без пароля сервер ничего не пересылает, даже с этой же машины (`PERMIT_DOCKER=none`); серые списки выключены — первый ответ клиента не должен ждать повторной доставки.
- **Ответы клиентов.** Сервис сам читает ящик `leads@` (IMAP на `127.0.0.1:993`, пароль — тот же сгенерированный): ответ клиента на письмо сайта попадает в переписку его заявки, с файлами, и приходит сотрудникам в Telegram. Письма, которые не к чему отнести, ждут решения в админке, раздел «Входящие», 30 дней. Подробности — [api/README.md](../api/README.md). Пароль `leads@` руками не меняется (`krokosha-mailbox passwd` для него откажет): сервис с неверным паролем попал бы под fail2ban собственного почтового сервера.
- **Исходящий порт 25.** Многие провайдеры закрывают его, пока не попросишь. Установщик проверяет и предупреждает: сайт работает, письма ждут в очереди, но наружу не уйдут.
- **Память:** контейнеру отведено до 768 МБ, в покое он занимает 300–450 МБ. На VPS с 2 ГБ это впритык — см. [architecture.md §7](../docs/architecture.md).

### DNS-записи

В конце установки печатается готовый список (он же — в `/srv/krokosha/mail/DNS.txt`):

| Запись | Имя | Значение |
|---|---|---|
| A | `mail` | адрес сервера |
| MX | `@` | `10 mail.<домен>.` |
| TXT (SPF) | `@` | `v=spf1 mx -all` |
| TXT (DKIM) | `mail._domainkey` | `v=DKIM1; k=rsa; p=…` — из установщика |
| TXT (DMARC) | `_dmarc` | `v=DMARC1; p=quarantine; rua=mailto:postmaster@<домен>` |
| SRV | `_imaps._tcp`, `_submissions._tcp`, `_submission._tcp` | `0 1 993 / 465 / 587 mail.<домен>.` — автонастройка почтовых программ |
| **PTR** | адрес сервера → `mail.<домен>` | ставится **не в DNS домена, а в панели провайдера сервера** («reverse DNS»). Без него крупные почтовые сервисы кладут письма в спам |

Почтовые программы: IMAP `mail.<домен>:993` (SSL/TLS), SMTP `:465` (SSL/TLS) или `:587` (STARTTLS), имя пользователя — адрес целиком. Thunderbird настраивается сам: сайт отдаёт `/.well-known/autoconfig/mail/config-v1.1.xml`.

Проверка после выкладки: письмо на Gmail и обратно, заголовки `spf=pass dkim=pass dmarc=pass`, затем [mail-tester.com](https://www.mail-tester.com) — цель ≥ 9/10.

### Письма в спаме

Сначала — что говорит сам получатель. В Gmail: письмо → «⋮» → «Показать оригинал».

- **SPF, DKIM или DMARC не `PASS`** — ошибка настройки: сверить записи с `/srv/krokosha/mail/DNS.txt` (`dig +short TXT mail._domainkey.<домен>`), проверить PTR (`dig -x <адрес>`).
- **Все три `PASS`, а Gmail пишет «ранее фильтры распознавали аналогичные письма как спам»** — дело в репутации, а не в настройке. У нового домена и нового адреса сервера истории нет, первые письма (особенно «test» / «test») Gmail встречает с подозрением. Настройкой это не лечится, только временем и нормальной перепиской:
  1. Проверять письмами с настоящим текстом, а не «test».
  2. У себя в Gmail: «Не спам», добавить адрес в контакты, ответить на письмо. Так Gmail учится доверять домену — сначала у этого получателя, потом и у остальных.
  3. Черные списки: `dig +short <адрес задом наперёд>.zen.spamhaus.org` и [MXToolbox](https://mxtoolbox.com/blacklists.aspx). Адрес, доставшийся от прошлого арендатора, бывает в списках — [Barracuda](https://www.barracudacentral.org/rbl/removal-request) и другие снимают по заявке владельца.
  4. [Google Postmaster Tools](https://postmaster.google.com): подтвердить домен TXT-записью и смотреть репутацию домена и адреса (данные появляются, когда писем на Gmail становится достаточно).
  5. Через 2–3 недели нормальной переписки письма всё ещё в спаме — отправлять наружу через релей с хорошей репутацией (smarthost: почтовый сервис транзакционных писем); это отдельная настройка, в установщике её нет.
- **Имя отправителя.** Письма подписываются `--mail-name` («Denis Humen»); без него — владелец из `content/site.yaml` («Denis (Krokosha)»). Поменять: `sudo ./install.sh --from-env --mail-name "Имя Фамилия"`.
- Что сайт сам делает для доставляемости, описано в [api/README.md](../api/README.md) («Письма»): подтверждение клиенту не повторяет присланный текст, ссылки только на домен сайта, одинаковые ссылки в тексте и HTML.

## fail2ban

- `sshd` — вход по SSH только по ключам, jail просто убирает шум.
- `krokosha-admin` — неудачные входы в админку: 10 за 15 минут → бан на час (повторные — дольше, до недели), только для портов 80/443. Источник — лог админки в nginx (ответы 401 и 429 на форму входа); API полный адрес нигде не хранит.

```bash
sudo fail2ban-client status krokosha-admin              # кто забанен
sudo fail2ban-client set krokosha-admin unbanip АДРЕС   # снять бан (например, свой)
```

## Фаервол и то, что уже живёт на сервере

Установщик трогает только своё (docs/architecture.md §5):

- Правило для SSH добавляется первым и проверяется **до** включения UFW; порт берётся из `sshd -T`.
- Открываются 80 и 443, с почтой — ещё 25, 465, 587 и 993; дополнительные порты — `--allow 51820/udp` (можно несколько, запоминаются).
- **WireGuard определяется автоматически:** для каждого интерфейса остаётся открытым его порт и разрешается маршрутизация клиентов (`ufw route allow in on wg0`) — по умолчанию UFW пересылаемый трафик отбрасывает. `net.ipv4.ip_forward` не меняется, NAT-правила не трогаются.
- `--skip-firewall` — не настраивать UFW вовсе.
